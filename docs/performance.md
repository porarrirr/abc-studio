# テンポ変換の高速化

2026-10-17。再生スケジューリング、バッファ先読み、WAV書き出しが共有する
`PlaybackSequence.seconds(forBeat:)` と、再生クロックの秒→拍変換を改善した。
従来は問い合わせごとにテンポ表の先頭から積分していた。
テンポ境界の累積秒を初期化時に保存し、二分探索で区間を選ぶことで、
問い合わせの計算量を O(テンポ数) から O(log テンポ数) に変更した。
追加メモリはテンポ境界ごとに Double 1個。テンポ表の変更時には索引も更新する。

## 再現方法

```sh
# 変更前: この最適化前のコミットのソースを指定する
git show fb00d5a:Sources/Audio/ABCSequencer.swift > /tmp/ABCSequencer-before.swift
sh scripts/benchmark_tempo.sh /tmp/ABCSequencer-before.swift

# 変更後
sh scripts/benchmark_tempo.sh
```

Apple M2 / macOS 27.0.1 / Xcode 27.0、Swift の `-O -whole-module-optimization`
で実行。アプリの Release と同じ最適化方式を使う。
ABCを実際にパース・シーケンス化した後、全音の開始時刻と終了時刻を100周計算する。
1回ウォームアップし、7回の中央値を採用する。入力生成・パース・シーケンス化は計時外。
テンポ変更のある16・256・1024小節と、テンポ一定の1024小節を測定する。
各小節は4音。出力のチェックサムでも計算結果を比較できる。

## 測定結果

以下は全音の時間変換100周分の中央値。改善率は `(変更前−変更後)/変更前`。

- テンポ変更あり・16小節: 0.079ms → 0.088ms（0.009ms増加）。小さい入力では探索の効果は出ない。
- テンポ変更あり・256小節: 21.906ms → 3.624ms（83.5%短縮）。
- テンポ変更あり・1024小節: 419.184ms → 20.455ms（95.1%短縮）。
- テンポ一定・1024小節: 0.623ms → 0.409ms（34.3%短縮）。

全ケースで変更前後のチェックサムは一致した。短い処理の絶対値は実行時の環境に左右される。

この測定は時間変換のCPUコストであり、起動時間、譜面描画、音声デコード、
WAV書き出し全体、端末上のフレームレートが同じ割合で改善することを示すものではない。
テンポ変更の多い長い曲ほど効果が大きく、テンポ一定の曲では従来どおり直接換算する。

## 正しさの検証

単体テストは変更前の線形積分と比較し、空・一定・多数のテンポ変更・同一拍の
テンポ変更・境界の前後・曲外への外挿・秒→拍の逆変換を確認する。
テンポ表の要素変更・追加・置換、および値型コピー後の独立性も検証する。

iOS 27.0 / iPhone 18 Pro Simulatorで単体テスト57件が成功（最終調整後に再実行）。
UIテスト3件も成功し、譜面表示・パート音量・再生停止・スクロール追従を確認した。

## 音声バッファとタブ復帰の高速化

2026-10-21。ゲイン処理とフェードを Accelerate のベクトル演算に変更し、
音源ごとのピーク値とフェード係数を再利用する。ピークが閾値以下の音符は
ソフトクリップの全サンプル走査を省く。閾値を超える音符は従来の曲線を保つ。
同じ音源・音程・フレーム数・ゲイン・フェード・クリップ設定の最終バッファは
NSCache で共有する（コスト上限16MB、256件）。返されたバッファは読み取り専用。

楽譜の組版結果も、ソース全文・曲番号・表示幅・ズームをキーにして最大3件、
描画図形の合計コスト60,000を目安に保持する。タブを離れてビューが破棄されても
同じ条件なら再組版を省く。ソース・回転・ズームが変わると組み直す。
再生カーソル更新ではソース全文のハッシュを毎回計算しない。

### 再現方法

```sh
git show 5087955:Sources/Audio/SoundFontPlayer.swift > /tmp/ABC-SoundFontPlayer-before.swift
sh scripts/benchmark_audio.sh /tmp/ABC-SoundFontPlayer-before.swift
sh scripts/benchmark_audio.sh
sh scripts/benchmark_layout.sh
```

Apple M2 / arm64、Swift の `-O -whole-module-optimization` で測定。
音声は同梱のピアノ音源 C4〜B4。音源を温めた後、音価がすべて異なる72音
（ベロシティ75）と、同じ12音を繰り返す72音（ベロシティ80）を各3回測り、
中央値を取る。最終バッファの再利用がない条件と、ある条件を分ける。

- 音価の異なる72音: 11.649ms → 4.847ms。約2.40倍、処理時間58.4%短縮。
- 同じ音符を繰り返す72音: 10.898ms → 0.071ms。約153倍。
- 512音の再組版とキャッシュ取得の比較（5回の中央値）: 2.389ms → 約0.001ms。

処理速度+120%の目標は2.2倍に相当する。上記の音声準備の測定では達成した。
初回の音源デコード、オーディオセッション起動、画面描画全体を含む実機の
応答時間が2.2倍になったという測定ではない。初回12音の生成はファイルキャッシュや
実行順による変動が大きく、この変更による短縮率は主張しない。

### 検証

変更前後の実装をmacOSで同じ音源に対して実行し、ピアノ・ヴァイオリン・フルート、
3音程、3フェード長、3ベロシティ、2ゲインの162条件で全サンプルを比較した。
最大誤差は0。音声キャッシュ再利用、スカラー計算との一致、設定変更時の再生成、
組版キャッシュの編集・幅・ズーム変更時の再計算を単体テストにも追加した。
iOSアプリ・テストターゲットの `build-for-testing` は成功。
シミュレータサービスが応答しないため、今回のiOSテスト実行と実機での音切れ・
スクロール確認は未完了。

## UIの描画と入力処理の負荷削減

2026-10-21。楽譜の各段を「カーソル」「固定の五線・文字・音符」「強調する音符」
のレイヤーに分けた。固定部分は Equatable な別ビューで保持し、再生位置だけの
変更では描画命令を作り直さない。強調レイヤーは対象音符の図形だけを描く。

ミキサーはパートの表示値を比較し、変わっていない行のビュー構築を省く。
楽器選択メニューも別の Equatable ビューにし、音量操作では再構築しない。
楽器の分類と同梱サンプルの一覧は再利用し、画面更新ごとの分類・リソース検索を省く。

エディタは変更後のUTF-16範囲を使って、変更を含む行だけ色付けする。
複数行の貼り付け・改行の削除も行全体を更新する。編集範囲が不明な操作や
IME変換では全文処理へ戻す。行数は一時的な行文字列の配列を作らず数え、
ソース変更時に保存して表示で再利用する。入力済みかの判定も全文のトリムを省く。

### 再現と測定結果

```sh
sh scripts/benchmark_ui.sh
```

Apple M2 / arm64、Swift `-O -whole-module-optimization`、同梱Bravuraを使い、
7回の中央値を測定した。

- 楽譜: 8パート、幅390。列に揃う複数パートの音符を同時に強調し、120回更新。
  全段描画79.247ms → 更新レイヤーのみ5.494ms（**93.07%短縮**）。
- エディタ: 5,000行、50回編集。色付け範囲判定と行数計算の合計。
  全文104.770ms → 変更行と行数計算6.680ms（**93.62%短縮**）。

この測定は更新処理のCPU時間で、GPU合成・UITextViewのレイアウト・タブの
アニメーションを含む実機のフレーム時間ではない。固定レイヤーの初回描画も
再生カーソルの更新時間には含めない。UI全体の体感速度が90%改善したという
実機測定は未実施。

### 検証

関連するリポジトリ内のXCTest 7件をmacOSホストでも実行し、すべて成功。
変更行と全文の色付け結果の一致（日本語・絵文字・複数行挿入・改行削除・空文書）、
改行種別ごとの行数、レイヤー描画の色・対象段の絞り込み、および既存の

## 画面切り替えと曲を開く操作全体の見直し

タブの切り替えは、毎回ビューを破棄して作り直す方式から、初めて開いた画面を
保持して再利用する方式へ変更した。未訪問の画面は生成しない。エディタの
UITextView・選択範囲・取り消し履歴、各画面のスクロール領域を保持する。
非表示の画面は操作・アクセシビリティ対象から外し、楽譜の再生カーソル更新と
エディタへのソース再設定を止める。再表示時に現在のデータへ追いつかせる。

曲を開く経路は、初期復元・Filesから開く・サンプル・ライブラリ・クリップボード・
エディタ反映で共通の準備段階を使う。読み出し、改行正規化、ABC解析、ビーム処理、
診断、初曲の演奏シーケンスと既定楽器の準備を専用キューで実行し、完了時にモデルへ
反映する。複数曲の選択もシーケンスを先に準備する。直近の文書は解析結果を再利用する。
音色だけを変更した場合は演奏シーケンスを作り直さない。

読み込みには世代番号を付け、後から選ばれた文書や編集された下書きを古い結果が
上書きしないようにした。初期復元は一度だけ行い、起動時にファイルを開いている場合は
その操作を優先する。準備中もタブ移動を続けられ、旧曲を誤って再生・シークする操作は
抑制する。再生中の旧曲は停止・一時停止できる。

楽譜の初回組版・幅変更・ズーム変更も専用キューへ移した。キャッシュにある組版は
そのまま表示し、古い要求の組版結果を表示しない。エディタの初回全文色付けは
判定をバックグラウンドで行い、UIへの属性反映を小さく分割する。色付けの操作は
ユーザーの取り消し履歴へ登録しない。

- macOSホストで共通の文書準備を含むXCTest 9件が成功。
- 下書き編集による読み込み取り消しと、後の文書選択を優先するモデルテストを追加。

  繰り返し往復 → 下書きと音量の保持 → 取り消し履歴の継続、を確認するUIテストを追加。

CoreSimulatorサービスを再起動してから再試行したが、デバイス検出がタイムアウトし、
`xcodebuild test` も実行先のシミュレータを見つけられなかった。したがって追加した

## 事前準備を使わない再生開始の短縮

2026-10-21。再生前に冒頭の音声を作る方式を取りやめ、再生を押した後の処理を
改善した。読み込み時の音声デコード・バッファ生成・エンジンの `prepare` は行わない。

- 音源ファイル全体ではなく、音価・余韻・ピッチ補間に必要な冒頭部分だけをデコードする。
  より長い音符では必要な長さを読み直し、予約済みのバッファは変更しない。
  キャッシュは音程ごとに最長の読み込み部分を保持し、長い音声を短い要求にも再利用する。
- 再生要求後のデコードを最大4本で並列化する。結果は元のイベント順に戻して予約する。
  世代番号による取り消しと、全パートが共有する開始時刻は維持する。
- 音声デコードと、セッション有効化・エンジン起動を並行して進める。
- 全バッファを予約してから指定する共通開始時刻の余裕を80msから10msへ短縮する。

### 再現方法

```sh
abc_file='/path/to/Symphony No. 1 in C Major - I. Allegro con brio (Full Orchestral Score).abc'
git show 574631b:Sources/Audio/PlaybackEngine.swift > /tmp/PlaybackEngine-before.swift
git show 574631b:Sources/Audio/SoundFontPlayer.swift > /tmp/SoundFontPlayer-before.swift
# 両方とも待ち時間0、事前準備なし。第4引数で変更前の音源処理も指定する。
sh scripts/benchmark_startup.sh "$abc_file" /tmp/PlaybackEngine-before.swift 0 /tmp/SoundFontPlayer-before.swift
sh scripts/benchmark_startup.sh "$abc_file" Sources/Audio/PlaybackEngine.swift 0
```

Apple M2 / macOS 27.0.1、Swift `-O -whole-module-optimization`。
依頼時の添付と一致するABC（9パート、816音）を解析して使用した。
毎回新しいエンジンと空の音源キャッシュを生成し、読み込み直後に再生する。
7回の中央値は **122.630ms → 30.436ms**。
約4.03倍（速度+303%、待ち時間75.2%短縮）で、速度+300%の目標を満たした。
個々の測定は変更前121.565–212.095ms、変更後19.483–83.118msと変動した。

計測区間は再生操作から、全パートに指定した共通ホスト時刻まで。
エンジンの `prepare`・起動、音声デコード、バッファ生成、開始余裕を含む。
解析と音声グラフ構築は変更前後とも計時外で、OSのファイルキャッシュは削除していない。
プレイヤーノードは予約と開始時刻を記録するものに差し替えている。
したがって実際の出力デバイスの発音遅延やiOSのセッション有効化時間を含む
実機のタップ→発音測定ではなく、すべての端末・実行で4倍になることは保証しない。

### 検証

変更前の音源処理と、ピアノ・ヴァイオリン・フルート・ホルン・ティンパニ、
5音程（音源の範囲外のピッチ補間を含む）、4音価、3ベロシティの300条件で比較し、
全サンプルの最大誤差は0だった。

iPhone 18 Pro / iOS 27.0 シミュレータで単体テスト69件が成功した。
読み込み時に音声生成が行われないことと、短い要求の後の長い要求でも音声が
切り詰められないことを単体テストに追加した。シーク、速度変更、再開、準備取り消し、
休符を含むパート間の同期も回帰テストの対象。実機での発音遅延と音切れ確認は未実施。
